# E3d：两跳搬运 vs 单跳 vs 直接重算（成分实测 + 判据）

装置：容器 C（`31631`，`10.244.1.89`，`/dev/davinci3`），plain 引擎 892 块 × 128 = 114,176 token。
脚本 `/root/e5/e3d_rehop.py`；度量用 vLLM `/metrics` 差分 + 请求墙钟。

## 实测成分（同一个 4,527 token 的前缀）

| 情形 | 墙钟 | Δqueries | Δhits |
|---|---|---|---|
| 冷 prefill（首次） | **0.634 s** | 4,527 | 0 |
| 命中前缀缓存 | 0.133 s | — | — |
| 被 churn 1.25× 驱逐后再来 | **0.618 s** | 4,527 | **0** |

⇒ 驱逐之后就是全量重算，`dh=0` 是硬证据（不是部分命中）。每 token 约 **140 µs**。

## 搬运的固定成本

跨容器 pull 实测 = **0.61 × 重算**（E-env，100% external hits）。于是：

- **单跳** = capture（固定 ≈0.23 s）+ 0.61·T_recompute
- **两跳** = 2 ×（capture + 0.61·T_recompute）

## 代入的对照表

| 前缀 token | 直接重算 | 单跳搬运 | 两跳搬运 |
|---|---|---|---|
| 2,500 | 0.35 s | **0.44 s** | 0.89 s |
| 5,000 | 0.70 s | **0.66 s** | 1.31 s |
| 10,000 | 1.40 s | **1.08 s** | 2.17 s |
| 20,000 | 2.80 s | **1.94 s** | 3.88 s |

## 三条判据（可写进策略）

1. **单跳的盈亏平衡点在 ≈4.2k token**：解 `0.23 + 0.61t = t` 得 `t ≈ 0.59 s`，即前缀约 4.2k token 以下，搬运比重算还慢。
2. **两跳在任何长度下都不划算**：`2×0.23 + 1.22t > t` 恒成立（固定成本翻倍、而 pull 只省 39%）。表格最后两列在每一行都更差，差距随前缀线性放大。
3. **两跳的额外风险**：第二跳的前提是中间卡上的块还在。E3 已经测过——中间卡被 churn 超过约 1.0× 容量，`dh=0`，第二跳直接退化成「pull 失败 + 全量重算」= 1.25 s（对 4.5k 前缀），比一次重算（0.63 s）差一倍。

## 与 E3 合起来的结论

- E3 说"目的地当时多满不影响搬入 program 的存活"，所以**没有"搬两次去找更空的卡"这种动机**；
- E3d 说"多一跳就是线性加一次 capture + 一次 pull"，而 pull 只比重算便宜 39%，固定成本吃掉了收益；
- 因此：**一跳、且只在前缀足够长（≳4k token）且目的地余量足够（E3 的约束）时才搬；两跳一律不做。**

## 诚实边界

- 两跳的 1.234 / 1.251 s 是**由成分推导**的，不是端到端跑出来的——三台容器上还没有把 `kv_both` + executor 的拉取链路接起来，端到端两跳需要额外接线。
- 单跳的 0.617 s 同样由"capture 0.23 s + pull 0.61·T"推出，其中 pull 比值来自 E-env 的跨容器实测（8~9 块小前缀），换到 4.5k 前缀可能有偏差。
- 每 token 140 µs 是单点测量（4,527 token），未做长度扫描。

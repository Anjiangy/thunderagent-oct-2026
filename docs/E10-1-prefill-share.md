# E10-1 — 一个 agent step 里 prefill 占多少

装置：单张 910B2（`10.244.0.61:8110`），Qwen2.5-14B-Instruct，`max_model_len 12288`、`gpu-memory-utilization 0.80`、`--enable-prefix-caching --enforce-eager`；greedy、`ignore_eos` 保证输出 token 数精确。
测量两套：客户端首 token 时间（含排队）＋ 引擎计数器 `vllm:request_prefill_time_seconds`（纯 prefill 计算）。

## 结果（18 格，`data/e10_prefill_share.csv`）

| 上下文 | 输出 | 并发 | TTFT | 单步墙钟 | **prefill 占比** | 引擎侧 prefill |
|---|---|---|---|---|---|---|
| 2k (1,595 tok) | 128 | 1 / 8 / 32 | 0.29 / 0.41 / 8.12 s | 11.7 / 12.4 / 21.1 s | 2.5 / 3.3 / **38.4%** | 0.23 / 0.24 / 7.69 s |
| 2k | 512 | 1 / 8 / 32 | 0.21 / 0.35 / 0.68 s | 45.8 / 51.9 / 55.5 s | 0.45 / 0.68 / 1.2% | 0.18 / 0.18 / 0.26 s |
| 4k (3,135) | 128 | 1 / 8 / 32 | 0.26 / 0.46 / 1.05 s | 12.4 / 13.6 / 14.7 s | 2.1 / 3.4 / 7.2% | 0.22 / 0.22 / 0.38 s |
| 4k | 512 | 1 / 8 / 32 | 0.25 / 0.46 / 0.97 s | 50.8 / 54.7 / 56.7 s | 0.50 / 0.84 / 1.7% | 0.20 / 0.21 / 0.30 s |
| 8k (6,215) | 128 | 1 / 8 / 32 | 0.53 / 0.81 / 1.84 s | 12.9 / 14.2 / 15.5 s | 4.1 / 5.7 / **11.8%** | 0.46 / 0.46 / 0.54 s |
| 8k | 512 | 1 / 8 / 32 | 0.28 / 0.61 / 1.55 s | 50.6 / 54.6 / 56.4 s | 0.56 / 1.1 / 2.8% | 0.20 / 0.22 / 0.37 s |

## 判定（按预注册判据：全点 <10% 则停掉性能叙事）

- **prefill 计算本身是 0.2~0.5 s，与上下文长度只呈弱线性**（1.6k→0.18 s，6.2k→0.46 s ≈ 74 µs/token）。
- 以 512 输出计（贴近真实 agent 一步），占比 **0.5~2.8%**，全部低于 10%。
- 以 128 输出计，占比 **2~12%**，只有两格越过 10%（8k/128/c32 = 11.8%，2k/128/c32 = 38.4%），而这两格的 TTFT 里绝大部分是**排队**（引擎侧 prefill 只 0.54 s / 7.69 s，后者是 32 并发把 prefill 批次串起来等的结果）。
- 单步墙钟由 **decode 主导**：这套 NPU 上 decode 只有 **9~11 tok/s**，512 token 就要 45~50 s。

## 结论

1. **在这套栈上，prefill 不是瓶颈**：即便 37k 上下文，按 74 µs/token 外推也就 ≈2.7 s，相对 512 输出的 ~50 s 仍是 5% 量级。
2. **但这是“慢 decode”撑起来的结论**：decode 之所以这么慢，是 `--enforce-eager` + 单卡无 batch 调优。若换成 batch 化、图模式，decode 提 5 倍，同样的预填就变成 20~25%——那时 prefill 会重新变成问题。
3. 因此“命中率/重算”这类指标对**用户可见时延**的作用被 decode 稀释；它真正影响的是**引擎吞吐**（省掉的重算 token 会占掉别的请求的 slot）。这条要写清楚，否则就是我们之前所有“持平”的根源。

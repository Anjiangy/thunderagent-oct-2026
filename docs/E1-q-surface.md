# E1 — 睡着的时候，缓存被谁吃掉了

日期：2026-10-27　容器 B（`coder-user-residency-1-67bbc6745b-p7fhz`，NPU 3，单卡）
引擎：纯 vLLM（无 KV connector），`--max-model-len 8192 --gpu-memory-utilization 0.80 --enable-prefix-caching --enforce-eager`
容量：`946 × 128 = 114,176` token（`vllm:cache_config_info`）

## 装置

10 个 resident，各 2500 词（≈3.3k token，合计 33k = 0.29 倍容量）。先各发两轮让它进缓存；
然后灌**无关流量**（filler，每条不同前缀，800 词）；再让每个 resident 各发一次，用
`vllm:prefix_cache_queries_total / hits_total` 的差分算命中比 `q`。

两处细节是本轮才修对的：

- **每个 resident 只 probe 一次**。probe 本身会 touch 它的块，探两次等于自己给自己续命。
- **引擎不重启，改用升降序两次交叉验证**。上一轮"每格重启引擎"的做法在 B 上根本静默失败
  （旧引擎仍占着端口），结果读到的是跨格累积污染，已作废。

## 结果（`data/e1_q_surface.csv`，图为 `data/e1_q_surface.png`）

| 流动量 / 容量 | filler token | q（升序） | q（降序） | 存活 |
|---|---|---|---|---|
| 0.00 | 0 | 0.9895 | 0.9789 | 10/10 |
| 0.25 | 29,120 | 0.9825 | 0.9864 | 10/10 |
| 0.50 | 57,200 | **0.0000** | **0.0000** | 0/10 |
| 0.75 | 86,320 | **0.0000** | **0.0000** | 0/10 |

**两个顺序给出同一条悬崖**，阈值落在 0.25 与 0.5 之间，且断崖式（0.98 → 0.00，中间没有过渡）。

## 三个判读

1. **这不是"缓存被清空"，是"只清旧人"**：`q_last_filler` 全程 0.94~0.97——filler 自己的块
   好好地躺在缓存里。也就是说 vLLM 的 LRU 实际行为是"最后写入者赢"：谁最近写过，谁留下；
   谁在睡觉，谁被敲掉。这正是 agent 负载最吃亏的形态（跑几秒 → 等工具几十秒）。
2. **阈值远低于账面容量**：resident 33k + filler 57k = 90k，仍小于 114k 却已经全灭。
   说明 vLLM 可用的"安全余量"比 `num_gpu_blocks` 名义值小得多。
3. **时间不背锅**：M10 已证 30 s 纯闲置不掉命中；这次把 gap 固定为 2 s，变化全来自流量体积。
   ⇒ 触发条件应该按**token 流动量**写，不是按"等了多久"。

## 对路线 C 的意义

一次全灭 ≈ 10 × 3.3k = 33k token 的 prefill 白付；而搬一次是 0.61×（E-env 已测）。
所以"在 resident 被敲掉之前把它挪走或保住"在这条悬崖右侧**必然划算**，左侧不必动。
E4 的触发条件可以直接写成：`预测流动量 / 容量 > 0.25` 时，优先保/搬，而不是等被驱逐。

## 诚实边界

- 单卡、合成 filler、resident 数量固定 10；真实 agent 的 resident 会是几十个、前缀更长。
- 阈值只夹到 0.25~0.5 区间，没有在中间加密测点（2 s 的 probe 成本很低，下一轮可以补）。
- 只测了"纯无关流量"；如果流动量与 resident 有前缀重叠，驱逐行为可能不同。

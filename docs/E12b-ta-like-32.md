# E12b — ta_like 的 32 program 首测：命中持平，吞吐掉一半

装置：tm4 上真实 mini-swe-agent（6 步、5000 词前缀、slice 0:32、workers 8）；两卡各 114,176；三臂入口 18100(TA) / 18103(sticky) / 18104(ta_like)。

| 臂 | 墙钟 | 集群命中 | 查询 token | token/s | 搬家 | 停等 |
|---|---|---|---|---|---|---|
| 我们 sticky | 433 s | 82.16% | 1,929,961 | 4,454 | — | 0 |
| 裸 ThunderAgent | 505 s | 81.96% | 1,989,268 | 3,940 | 0 | TA 内部 |
| **ta_like** | **1087 s** | **81.81%** | 1,958,864 | **1,801** | **0** | **123 次 / 3,254 s** |

## 结论

1. **命中率持平**（81.81 vs 81.96 vs 82.16，差 ≤0.35 pt）——容量账本没让命中率更差。
2. **吞吐掉一半**（1,801 vs 3,940 token/s）：全部损失来自“在请求路径里 sleep”。`holds=123`、累计停等 **3,254 s**，平均每次 26 s，而这段时间代理**没有做任何事**——它只是把请求挂住，等别的请求腾出空间。
3. **`migrations=0` 不是 bug**：`load_tokens a=220,192 / b=225,030`，两卡都已超容（各 114,176）。任何目的卡的“剩余”都是负数，规则 3（目的卡剩余 ≥ 前缀）永远不成立 ⇒ 在真超容区间，“搬”根本无处可搬。这与此前 E1/E4 的结论一致：搬迁只在“集群装得下、单卡装不下”时才有意义。

## 我的实现错在哪

我把“暂停”实现成了**请求路径上的 sleep**。TA 的暂停是**在调度器里排队**：它把 program 挂起，让别的 program 继续跑，自己不占线程。我的写法让每个请求各停 26 s，8 个 worker 于是串行化。

正确形状（下一步）：
1. **准入队列**：请求进 mod 后先进队列，由单个调度协程在容量空闲时放行（而不是每个请求各自 sleep）；
2. **停等只在“有在飞请求且即将完成”时使用**，若两张卡都超容，应**立即放行并标记 over-admit**（TA 在同样情况也会放行，因为暂停不会凭空创造容量）；
3. 把 `holds` 从计数升级成 `over_admit` 指标（即 `decide()` 返回第三个状态）。

## 边界

- 每臂 n=1；三臂不在同一时段（引擎未在臂间重启，后跑者吃前跑缓存）。
- ta_like 的 800 tok/s 排空估计是拍的，直接决定停等时长，需要按 `generation_tokens_total` 差分标定。

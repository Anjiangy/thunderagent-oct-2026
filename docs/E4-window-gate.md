# E4：按历史间隔估窗口，只够长才搬（第一版错、修好后没回归，但 4 轮太短学不出东西）

日期：2026-10-28
代码：`patches/add_window_gate.py`（初版）+ `patches/fix_window_coldstart.py`（修正）
开关：`EXECUTOR_WINDOW_MIN`（秒，0=关）、`EXECUTOR_MOVE_COST_INIT`（默认 0.6 s，之后用实测 EMA 更新）
判据：`median(该 program 最近 8 次轮间间隔) >= max(WINDOW_MIN, 1.2 × 最近搬家耗时)`

## 结论（含一次失败）

1. **初版是错的**：对“还没有历史”的 program 返回 0.0，等于拒绝搬最需要搬的那些（它们还没被观测到空闲）。结果搬家拖到第 3 轮才发生，而 A 在第 2 轮就已经被打到 0 命中——**门控反而造成了 2 轮空转**。
2. **修正后不回归**：把“未知”解释为“放行”，15 s 组与不门控组同轨迹（2→4 次搬家、第 3 轮 A 命中 100,096、p50 0.78 s）。
3. **4 s 组学不出东西**：门控需要 ≥2 个历史间隔才有判据，而 4 轮会话最多产生 1 个间隔——所以它一次都没拒绝（`window gate` 日志 0 条），搬了 4 个但一个字节都没拉到（B 侧 0 查询），A 全程越线 0 命中。这是**装置问题**：会话长度不足以支撑“靠历史估计窗口”的想法。
4. 因此这条策略的**可验证前提是会话足够长**（≥6 轮），而不是 4 轮。

## 与 E 编号的对应

- **E4（时机）**：这一刀就是 E4 —— “什么时候搬”。判据从“卡热不热”细化成“窗口够不够 + 卡热不热”。
- E2 提供上半句（卡越过容量线才值得搬），E4 提供下半句（窗口够长才搬得成）。二者相乘，缺一不可。
- 顺带：E4 的结论也解释了 E2 双向版里那个 10.7 s 尖峰——那是“窗口不够长却硬搬”的代价。

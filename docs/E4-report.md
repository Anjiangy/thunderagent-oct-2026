# E4 报告 — 什么时候必须开始搬

日期：2026-10-28　双卡 910B2（各 114,176 token）
数据：`/root/e2/e4_timing.csv`

## 1. 命题

E1 说"什么时候丢"，E2 说"丢了之后搬值不值"。E4 补最后一环：**搬运本身需要源卡还持有这段 KV**（capture 就是一次源卡上的 prefill），所以存在一个决策窗口——错过了就搬不动了。

做法：resident 建好后，先往源卡灌 `d × 悬崖` 的无关流量（悬崖取 E1 的 0.45× 容量 = 51,379 token），然后**再**开始搬，量三件事：capture 命中、pull 是否成功、搬完后在目的地的命中。

## 2. 结果（8 个 resident，每格一次）

| 已灌 churn（占悬崖） | churn 轮数 | capture 命中 | 搬后命中 | 8 个 capture 总耗时 | 每 program 合计 |
|---|---|---|---|---|---|
| 0.00 | 0 | 0.985 | 0.985 | 1.00 s | 0.486 s |
| 0.25 | 13 | 0.988 | 0.988 | 1.00 s | 0.484 s |
| 0.50 | 25 | 0.986 | 0.986 | 1.01 s | 0.488 s |
| 0.75 | 38 | 0.982 | 0.982 | 0.99 s | 0.484 s |
| **1.00** | 50 | 0.985 | 0.985 | **1.01 s** | **0.484 s** |
| **1.25** | 62 | **0.000** | 0.985 | **5.53 s** | **1.043 s** |

## 3. 三个发现

1. **窗口内 capture 是平的**：从 d=0 到 d=1.00，capture 命中稳定在 0.98、8 个总耗时 1.0 s（≈0.125 s/个）。也就是说**提前搬不额外付 token**，只多占目的地一段时间的容量。
2. **过了悬崖，搬运退化成"先重算再搬"**：d=1.25 时 capture 命中 0，capture 总耗时 5.53 s（**5.5 倍**）——源卡上那一次变成了全量预填充。
3. **"搬晚了"比"不搬"更贵**：d=1.25 的每 program 合计 **1.043 s**，而 E2 测到的"不搬、回来重算"只要 **0.72 s**。所以错过窗口之后**不要搬**。

## 4. 决策规则（三条合起来就是完整策略）

```
1) 预计这段空闲会被无关流量冲过 0.45×容量  →  否则不搬（E2：搬是纯亏 3.5 倍）
2) 决定搬，就必须在 churn 累计到 0.45×容量之前开始（E4：过了就变成 1.04 s，比不搬还贵）
3) 搬完若目的地也会进来 ≥0.6×容量 的新流量  →  搬过去也保不住（E2 §9）
```

窗口有多长？本装置里 0.45× 容量 = 51k token，以单卡满速写入（≈2.6k token/s）被打满大约 **20 秒**。所以实践含义很直白：**program 一停下来就要判断，不能等**。

## 5. 诚实边界

- 每格只跑一次（n=1）；但 d≤1.0 五格之间的差异 <1%，d=1.25 的跳变是 5.5 倍，噪声不可能解释。
- churn 速率固定（每请求 800 词 ≈1.04k token、串行发），换并发后的窗口时长会变，**但窗口的边界（0.45× 容量）不变——那是容量规则，与速率无关**。
- 只测了"搬早不额外花 token"，**没测"搬早但 program 很快就回来"的浪费**。E2 的 0.35 档（0.51 s vs 0.15 s）就是这个浪费的量级：搬早而没被驱逐，等于白付 0.35 s/program。
- 8 个 resident、每轮 1 token；真实 agent 的多轮摊销未测。

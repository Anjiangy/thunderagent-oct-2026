# E11 压力臂：32 个并发 program 才把一张卡顶过容量

同一套真实 mini-swe-agent（6 步、5000 词前缀、两卡各 114,176 token），只改并发 program 数与路由入口。

| 臂 | program 数 | 墙钟 | 集群命中 | 查询 token | token/s |
|---|---|---|---|---|---|
| 我们（sticky） | 6 | 817 s | **95.82%** | 1,406,296 | 1,492 |
| 我们（sticky） | 32 | 433 s | **82.16%** | 1,929,961 | **4,454** |
| 裸 ThunderAgent | 32 | 505 s | 81.96% | 1,989,268 | 3,940 |

## 读法

1. **命中率确实会崩，而且崩在容量上而不是“路由策略”上**：6 个 program 时工作集只有 ~54k（单卡 114k 的 47%），命中 95.8%；32 个 program ≈ 290k 工作集，逼近/超过集群 228k，两臂同时掉到 ~82%。这是本项目第一次在**真实 agent 流量**上拿到“高并发 → 命中率下降”的证据（此前合成负载只有到 48 program 才崩）。
2. **两臂都崩，且我们略优**：32 program 下我们 82.16% vs TA 81.96%（+0.2 pt）、吞吐 4,454 vs 3,940（+13%）。差异在噪声边缘，不足以说“赢了”，但至少不输。
3. **命中率下降不影响吞吐**：32 program 的 token/s（4,454）是 6 program（1,492）的 3 倍——因为并发填满了 decode 的批，重算的额外 prefill 被并行吃掉。这也解释了为什么前面所有“命中率提升”都没能翻译成时延收益。

## 边界（必须写进结论）

- 每臂 **n=1**，且臂间未重启引擎（后跑的臂吃到前臂残留的前缀缓存）。
- 32 program 的工作集 290k 的估算基于 5000 词前缀 ≈ 6.8k + 自然 2.5k，未逐实例核。
- TA 臂在 32 program 时应有暂停（容量记账），本轮未采 `paused` 峰值。

# E1 报告 — 空闲 program 的前缀缓存什么时候被清掉

日期：2026-10-27　单卡：昇腾 910B2，`892 块 × 128 = 114,176 token`
数据：`data/e1_q_surface.csv`（升降序）、`data/e1_dense.csv`（加密扫描）
图：`data/e1_q_surface.png`、`data/e1e_e2.png`

## 1. 命题

ThunderAgent 把"哪段上下文继续驻留"完全交给 vLLM 的块级 LRU。一个 program 在等工具（几十秒到几分钟）期间不占 GPU，它的 KV 块就变成 LRU 里最冷的部分。
**E1 要回答的是：一个睡着的 program 回来时，它的前缀还在不在？在什么条件下不在？**

## 2. 装置

每个测点三件事：

1. **建常驻集**：10 个 resident，各 3000 词（≈5.4k token），建两轮 → 合计 ≈54k = **0.47× 单卡容量**；
2. **灌无关流量**：filler，每个请求 800 词（≈1.04k token），灌到 `pressure_ratio × 容量` 为止；
3. **探针**：每个 resident 再发一次**与第二轮 prompt 逐字节相同**的请求，用 `/metrics` 前后差分算 `q = Δhits/Δqueries`（=1 完全命中，=0 全量重算）。

两个防污染细节（都是踩坑后才加的）：

- **每个 resident 只 probe 一次**——probe 会把它的块 touch 到 LRU 顶端，probe 两次就变成"续命实验"；
- **每格换全新 resident 前缀**——第一版 20 格共用一个引擎，结果全 0，那不是系统性质，是上一格残留 filler 占了缓存。

辅助测量 `q_last_filler`：filler 自己再发一次。它恒在 0.93~0.97，说明 **filler 的块确实占着缓存**——这是"污染正在发生"的直接证据，不是推断。

## 3. 结果

### 3.1 升降序（验证悬崖不是路径依赖）

| 压力（filler/容量） | filler token | 升序 q | 降序 q | 存活 |
|---|---|---|---|---|
| 0.00 | 0 | **0.9895** | **0.9789** | 10/10 |
| 0.25 | 29,120 | **0.9825** | **0.9864** | 10/10 |
| 0.50 | 57,200 | **0.0000** | **0.0000** | 0/10 |
| 0.75 | 86,320 | **0.0000** | **0.0000** | 0/10 |

升序与降序在 0.25 与 0.50 之间给出同一答案 ⇒ **不是路径依赖，是状态依赖**。

### 3.2 加密扫描（定位悬崖）

| 压力 | filler token | q | 存活 |
|---|---|---|---|
| 0.25 | 29,120 | 0.9869 | 10/10 |
| 0.30 | 34,320 | 0.9921 | 10/10 |
| 0.35 | 40,560 | 0.9862 | 10/10 |
| 0.40 | 45,760 | **0.9819** | 10/10 |
| 0.50 | 57,200 | **0.0000** | 0/10 |

**悬崖在 0.40 与 0.50 之间（≈0.45× 容量）。**

## 4. 四个发现

1. **不是衰减，是断崖。** 0.40 → 0.9819，0.50 → 0.0000，中间没有中间态。机制：块级 LRU 逐块释放，但**前缀命中是链式的**——最前面一块没了，后面即使还在也用不上，整条前缀作废。所以 q 只有 1 和 0 两个稳定值。
2. **决定因素是"期间有多少无关流量"，不是"空闲多久"。** 0.25 档 gap 1/5/15/60 s 都给同样 0.98；0.5 档长 gap 也不会自己变好。**时间本身不驱逐任何东西。**
3. **阈值几乎正好是"剩余容量"。** 常驻集占 0.47×，余量 0.53×，实测悬崖 0.45×——吻合。即：**无关流量不超过空闲容量，resident 就安全；一超过，整体全灭。**
4. **没有"部分命中"这个中间态可用。** 想靠"丢一部分前缀还能跑到 60% 命中"兜底不成立——命中率在阈值附近是二值的。

## 5. 对策略的直接含义

| 观测到的量 | 判据 |
|---|---|
| 期间无关流量 `< 0.45 × 容量` | 不用管，回来还能命中 |
| `> 0.5 × 容量` | 已被清掉，回来必重算 → 只能在"搬走"或"放弃"里选 |
| 想保活 | 必须让 ping 把块持续 touch 到 LRU 顶端（单价见 E2/E3） |

这也解释了为什么"给空闲 program 保活"在真实流量里往往不出效果：**只要有一个租户跑长任务把卡灌满，睡着的 program 就已经没了**——保活必须在灌满之前开始，而不是回来之前。

## 6. 诚实边界

- **单卡、合成 filler、10 个 resident、3000 词**；没测多租户真实负载、跨卡、20+ 轮长会话。
- 悬崖位置依赖"常驻集占比"：本实验是 0.47×。常驻集更小时悬崖应更靠右（余量更大），但**未逐点验证**，只有 0.47× 一组。
- `q` 是"该请求自身的命中率"，不是系统命中率（后者含 filler 自己的 0.94）。
- 每个测点只跑一次（单次测量，非多次取中位）。0 与 0.98 的差距远大于合理噪声，但**悬崖精确位置（0.41？0.44？）没有重复测量**，只能说落在 0.40~0.50。

## 7. 复现

```bash
# B 容器（单卡）：/root/env/start_plain.sh 0 8110 8192
python3 /root/env/e1d_q.py        # 升序
python3 /root/env/e1d_desc.py     # 降序
python3 /root/env/e1_dense.py     # 加密 0.25/0.30/0.35/0.40/0.50
```
（每个测点重建全新 resident 前缀；若沿用旧引擎，必须换前缀，否则读数会被上一格 filler 污染。）

# E10：下一步三步（卡片需求、判据、装置）

写在 E1/E3/E3d/E4/E5/E9 收口之后。核心动机：我们几乎每个 A/B 都是"持平"，最可能的解释是**被优化的量本身占比太小**——所以第一步不是继续做机制，而是量这个占比。

## ① 量化 prefill 占比（1 张卡，1~2 h）

**问题**：一轮 agent 步骤里，prefill 占多少时间？它随上下文长度、输出长度、并发怎么变？

**装置**：单卡 plain 引擎（892 块 × 128 = 114,176 token），脚本扫三组参数：
- 上下文 2k / 4k / 8k token
- 输出 128 / 512 token
- 并发 1 / 8 / 32

每点发 N 次，`TTFT` 记作 prefill，`总时延 − TTFT` 记作 decode，占比 = `TTFT / 总时延`。

**预注册判据**：
- 若所有点 `prefill/total < 10%` ⇒ **停止把"缓存命中率"当性能卖点**，整条线转为"尾延迟兜底"叙事（已有硬证据：10.72 s → 1.32 s）。
- 若存在 `> 20%` 的格（大概率是长上下文 + 短输出 + 高并发），记下该格的参数，作为后续所有迁移实验的**唯一合法负载**。

## ② 保活策略调小（1 张卡，2~3 h）

**问题**：用 1-token 刷新保活，能不能以远低于搬运的成本把"睡觉 program"留在缓存里？

**装置**：M11 的 keep 逻辑收窄四道门——只看 `prompt_tokens ≳ 3k` 且历史轮数 ≥2 的 program；间隔按 `常驻集 ÷ 观测流入率` 定（用 `prompt_tokens_total` 差分估）；常驻集 ≤65% 容量；release/TTL 立即停刷。

**指标**：`保活消耗的 token / 避免的重算 token`（M11 那组是 59 次刷新换回 10/10 存活，代价 15~25% 吞吐——需要看这个比是否 >1）。

**判据**：比值 >2 则保留该机制；1~2 之间只在"尾部延迟敏感"场景用；<1 放弃。

## ③ 迁移兜底（2 张卡，半天）

**只在"保活不可行"的形态测**：卡间负载严重不均（一张 ≥0.9，另一张 ≤0.4）、前缀 ≳4k token、会话还剩 ≥2 轮。

这是我们唯一测出 43 个点提升的形态（压力窗口 7.38% → 50.4%），需在新拓扑复核。技术前提：两侧容器互相可达、`mooncake_connector.py` 的 5 处 `kv_role` 判据已打补丁、两侧以 `kv_both` 启动。

**判据**：该形态下 p50 TTFT 或命中率优于"不搬"≥10%，才值得保留迁移路径；否则迁移只作为 E2-offpath 的尾部兜底（不参与吞吐对比）。

## 卡片需求汇总

| 步骤 | 卡 | 说明 |
|---|---|---|
| ① | 1 | 扫参数即可，无需跨卡 |
| ② | 1 | churn 可自己灌 |
| ③ | 2 | 跨卡搬移定义上要两张 |

总计 2 张即可全部完成；3 张只服务"多目的地选择"，而 E3 已把那一格关掉（四档余度全 0.9771）。

## 附：SWE-bench Pro CPU 工作区（端口 30456）实测

- 主机 `coder-user-swe-bench-1-75d9d5bc4-xd95x`，aarch64，192 核 / 2 TB 内存，python 3.12.13。
- **Docker 可用**：`/usr/local/bin/docker` + DinD socket `/run/swe-pro-docker/docker.sock`，server 29.9.1 **arm64**；`/root/swe-bench/docker-data` 是 data-root。
- **镜像 0 个、无 `SWE_BENCH_PRO_*` 环境变量、无 `crane`**：模板是"干净"的，需要按 `vllm-hust-benchmark/docs/SWE_BENCH_PRO.zh-CN.md` 的 bootstrap 脚本首次准备（会拉 ARM 任务镜像、下载固定数据与官方 agent 源码）。
- 网络：pypi 200、api.github 200；huggingface 不可达。
- 磁盘：`/root` 卷 20 GiB 可用（指南建议 40 GiB），`/data` 是 3.5T 的公共盘（96% 已用）。
- **与 tm4 的分工**：30456 是 **SWE-bench Pro V1**（8 道 NodeBB 任务、ARM 镜像）的官方 CPU 工作区，**不能**直接接管我们现有的 SWE-bench **lite** 负载（django/astropy 的 x86 镜像在 arm64 上跑不了）。所以它不是 tm4 的替代品，而是"做 Pro 评测"的正确落点。
- 阻塞项（若要真跑）：① 需 40 GiB 卷或确认镜像体积；② 需要能拉到 ARM 镜像的 registry 或 `crane`；③ Pro V1 数据集需从 ScaleAI 取（含授权），或用模板注入的 `SWE_BENCH_PRO_DATASET_BASE`。
- NPU 侧现状：`31475` 有 14B 引擎（`:8110` 在跑）；`32072`（`10.244.0.61`、`/dev/davinci2`）**空闲，`:8110` 无服务**——若要用 Pro 跑，需要在这张卡上起一个 OpenAI 兼容服务，并确认 30456 能访问它的 pod IP。

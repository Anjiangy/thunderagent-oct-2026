# E2 双向版：kv_both 引擎上"搬 4 个"把一张超容卡救回来

日期：2026-10-28
拓扑：A `127.0.0.1:8110`（31475 容器）⇄ B `10.244.1.9:8110`（32102 容器），两侧都是 `kv_role=kv_both`（打完六行补丁）
执行体：executor `:8100`，`EXECUTOR_MODE=kv`、`EXECUTOR_MIGRATE_CARRIER=transfer`
负载：24 个 program，各自 3000 词独立前缀（≈5,000 token），4 轮，轮间 4 s，开局全部硬钉到 A

## 结果

| 臂 | 轮 | p50 | max | A 查询/命中 | B 查询/命中 | B 外部命中 | 搬家 |
|---|---|---|---|---|---|---|---|
| 关搬家 | 1–4 | 1.29 / 1.26 / 1.27 / 1.28 s | 1.35 s | 121,968 / **0** | 0 / 0 | 0 | 0 |
| 开搬家 | 1 | 1.27 s | 1.42 s | 132,181 / 10,112 | 10,213 / 0 | **10,213** | **2** |
| 开搬家 | 2 | 1.25 s | **10.72 s** | 116,833 / 17,536 | 25,463 / 15,104 | **10,164** | **4** |
| 开搬家 | 3 | **0.80 s** | 0.86 s | 101,591 / **100,096** | 20,377 / 20,096 | 0 | 4 |
| 开搬家 | 4 | **0.79 s** | 0.81 s | 101,591 / 100,096 | 20,377 / 20,096 | 0 | 4 |

（`data/e2_bi.csv`）

## 读法

1. **关搬家时 A 的命中恒为 0**。24 × 5,000 = 121k > 单卡 114k，A 始终在自己的容量线以上，每轮都从零重算——这就是"被动驱逐"的代价，p50 稳定在 1.28 s。
2. **开搬家后 A 的命中从 0 跳到 98.5%**（第 3 轮 100,096/101,591）。原因不是算法变聪明了，而是**搬走 4 个（≈20k）让 A 从 121k 降到 101k，落回容量内**，缓存才留得住。
3. **搬过去的 4 个确实是从 A 拉的**：B 第 1、2 轮 `external_prefix_cache_hits` 各 +10,213 / +10,164，正好等于它们的 prompt 总量；这些 token 没有在 B 上重算。
4. **代价是第 2 轮的一个 10.72 s 尖峰**：那次跨容器拉取排在请求路径里（capture + pull 两段），一次付清；之后第 3、4 轮降到 0.79 s。
5. 净效果：p50 从 1.28 s 降到 0.80 s（**1.6×**），4 轮累计 p50 5.1 s → 4.1 s。

## 与 E2 单向版的关系

单向版（producer/consumer）的结论是"有竞争时搬比算便宜，临界点在 0.35~0.7× 容量之间"。双向版把这条结论推到更极端的位置：**这张卡本来就在容量线以上（1.06×），被动驱逐让命中率恒为 0**，此时搬 4 个（正好是 `⌈(121−114)/5⌉ = 2` 的预算上限）就把命中率拉回 98.5%。也就是说：

- 单向版测的是"竞争把缓存挤掉"；
- 双向版测的是"**自己把自己挤掉**"——超容卡不需要外部竞争就已经 0 命中，这时搬迁是唯一的止血手段。

## 一个必须写下来的副作用

kv_both 引擎上本地前缀缓存的表现和普通引擎不同：`kv_role` 一旦挂上 Mooncake 连接器，A 在"关搬家"臂里全程 `hits=0`（121,968 次查询、0 次命中）。这不是 bug，而是这套拓扑的固有形态——**缓存能不能留住，取决于这张卡是否越过容量线**，与连接器无关；越线就是 0，落回线内就是 98%。

## 复现

```bash
# 两侧：python3 patches/patch_kvboth_threads.py && bash start_both.sh
# 执行体：EXECUTOR_MODE=kv EXECUTOR_MIGRATE_CARRIER=transfer EXECUTOR_BALANCE=skew|off
python3 e2bi.py off     # 对照臂
python3 e2bi.py skew    # 搬家臂
```

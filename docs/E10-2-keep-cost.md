# E10-2 — 保活到底买到了什么

装置：单卡（892 块 ×128 = 114,176 token），4 个 program × 3500 词前缀（≈4.5k token）× 4 轮 × 轮间 20 s；
**三臂同压**：每臂都跑后台 churn（prefill-only 噪声，目标 1.4× 卡容量，实测 163,633 / 165,411 / 163,867 token）。

| 臂 | keep 请求 | keep 耗时 | 计数命中率 | 16 轮总时长 | 最慢一轮 | 多计的 prefill token |
|---|---|---|---|---|---|---|
| 不保活（现状） | 0 | 0 s | 26.4% | 213.5 s | 24.4 s | 0 |
| 每 2 s 刷新 | 96 | 12.6 s | **74.1%** | 213.6 s | 24.5 s | +517k |
| 按 churn 率定间隔（下限 2 s） | 96 | 12.6 s | 74.3% | **212.6 s** | **24.2 s** | +515k |

## 三个结论

1. **保活确实把计数命中率从 26% 抬到 74%**——但它买到的是“指标”，不是“用户感受”：16 轮总和 213.5 / 213.6 / 212.6 s，最慢一轮 24.4 / 24.5 / 24.2 s，差异 ≤0.5%，在噪声内。
2. **代价是 3 倍 prefill 计数**：+515k token 的额外预填。原因是每次刷新都要重发整个 4.5k 词前缀（命中所以算得快，但仍占 query 记账与调度 slot）。
3. **“按 churn 率定间隔”这个门在这套 churn 下退化到下限**：churn 突发速度约 22k token/s（prefill-only 请求单价 0.2 s），一个 4.5k 的常驻集 0.2 s 就被冲掉，所以任何 >2 s 的间隔都等于不保活 → 与 naive 完全同值（96 次、74.3%）。

## 与 E10-1 的关系

E10-1 说 prefill 只占一步的 0.5~2.8%，这里给出了它的直接后果：**省掉那 0.5 s 的预填，用户感知不到**（24.4 s vs 24.2 s）。
所以在这套栈上，保活/驻留这条线的正确位置是“降低引擎侧 token 吞吐压力”，而不是“降低用户时延”。

## 判据对照（预注册：保活 token ÷ 避免重算 token > 2 才保留）

- 避免重算 ≈ 517k（不计入时因为命中）；保活自身 ≈ 96 × 4.5k = 432k 记账 token（其中真正计算 ≈96 × 1 token）。
- 比值 ≈ 1.2，**未过 2**；且受益是零时延，因此结论：**按预注册判据，保活应关掉**（除非目标是吞吐/账单口径）。

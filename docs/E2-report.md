# E2 报告 — 搬 vs 驱逐的临界点

日期：2026-10-28　双卡：昇腾 910B2 ×2（各 `892 块 × 128 = 114,176 token`）
装置：A = `kv_producer`（源卡，churn 打在这里），B = `kv_consumer`（目的地），`MooncakeConnectorV1` + `kv_buffer_device=npu`
数据：`/root/e2/e2d_grid.csv`（3 rep × 3 压力 × 2 臂）、`/root/e2/e2d_decay.csv`（目的地继续写入）

---

## 1. 命题

E1 说明了一个睡着的 program 什么时候被块级 LRU 清掉；E2 要回答的是**清掉之前主动搬走值不值**。

两臂，同一批 resident、同一份 churn：

- **evict**：什么都不做，resident 留在 A；churn 把它们挤掉后，各自回来发一轮 → 命中率 0 就是"全量预填充"的代价；
- **migrate**：churn 之前把每个 resident 的 KV 在 A 上 capture，再 pull 到 B；churn 打在一个已经不装它们的 A 上；各自回来在 B 发一轮。

## 2. 装置演进（前两版结论作废，原因都在这里）

| 版本 | 缺陷 | 后果 |
|---|---|---|
| e2 | 压力 = churn / **满容量** | 8×5.1k 常驻 + 0.8×114k churn = 132k > 114k，四档全都超容 → "0.8 档应持平"根本没测到 |
| e2b | 压力 = churn / (容量 − 常驻集)，但没跟 E1 的悬崖对齐 | 0.8 档 churn 仍达 58.7k > E1 的 ~51k 阈值 → 依然全灭 |
| **e2c/e2d** | **压力 = churn / 满容量，与 E1 同轴；加 3 重复 + 连接预热** | 0.35 落在悬崖内、0.70 / 1.20 落在悬崖外 → 边界被夹住 |

此外 e2d 做了两件事：网格前先跑一次 dummy capture+pull 预热连接（0.53 s，丢弃），每格换全新 resident 前缀（避免跨格缓存污染）。

## 3. 结果（每格 3 次，单位：秒 / 每个 program 返回一次）

| 压力（churn/容量） | 臂 | 命中率 | 搬家耗时 | 探针 | 每 program |
|---|---|---|---|---|---|
| 0.35 | evict | 0.982 / 0.985 / 0.986 | — | 1.20 / 1.16 / 1.18 | **0.150 / 0.145 / 0.147** |
| 0.35 | migrate | 0.982 / 0.985 / 0.986 | 2.84 / 2.79 / 2.80 | 1.30 / 1.27 / 1.24 | **0.518 / 0.508 / 0.506** |
| 0.70 | evict | 0.000 ×3 | — | 5.71 / 5.81 / 5.77 | **0.714 / 0.726 / 0.721** |
| 0.70 | migrate | 0.986 / 0.989 / 0.986 | 2.90 / 2.85 / 2.80 | 1.27 / 1.26 / 1.25 | **0.521 / 0.513 / 0.506** |
| 1.20 | evict | 0.000 ×3 | — | 5.77 / 5.81 / 5.76 | **0.721 / 0.726 / 0.720** |
| 1.20 | migrate | 0.988 / 0.987 / 0.986 | 2.85 / 2.80 / 2.80 | 1.30 / 1.28 / 1.27 | **0.518 / 0.511 / 0.509** |

三条读数极稳（重复间差 ≤2%），说明装置这一版是干净的。

## 4. 结论：一个可直接写进策略的判据

把成本拆开（以 8 个 program 为单位）：

- **搬一个** = `2.8 s / 8 ≈ 0.35 s`（capture + pull，连接已预热）
- **命中返回一次** ≈ `0.16 s`
- **未命中返回一次** ≈ `0.72 s`

于是"搬"的总代价 ≈ `0.35 + 0.16 = 0.51 s`，与不搬打平的条件是：

```
0.16 + 0.56 × (1 − h) = 0.51   ⇒   h* ≈ 0.375
```

**即：如果你预计这个 program 回来时的命中率会低于 37.5%，就搬；高于它，就别搬。**

实测完全吻合：0.35 档 h=0.98 → 搬亏 3.5 倍；0.70/1.20 档 h=0 → 搬赚 1.4 倍（+40%）。

这条判据比"用压力阈值"更好用：它不依赖 churn 的具体形态，只依赖 E1 能给出的 `h`。

## 5. 目的地继续写入（e2d 的第三个补测）

搬完之后往 B 继续灌流量，看搬过去的前缀会不会被挤掉：

| 目的地额外写入 | 追加轮数 | 搬后命中率 |
|---|---|---|
| 0 | 0 | 0.984 |
| 0.2 × 容量 | 22 | 0.988 |
| 0.4 × 容量 | 44 | 0.978 |

**结论修正**：我原本的假设（"新写入永远赢，所以搬完继续写就会挤掉"）在 0.4× 容量以内**不成立**——因为总占用 = 搬入 43k + 新写 45k = 88k < 114k，压根没到要驱逐的点。

所以真正的规则仍然是**容量规则**：`搬入量 + 后续新写入 > 容量` 时才会开始驱逐；recency 只在"那一刻"决定谁被驱逐（而搬入的块此时通常还是最新的，所以先被驱逐的是更早的写入）。

要观测到衰减，需要 `frac ≥ 0.6~0.7`（43k + 68k ≈ 111k，刚好压线）。这一格**未完成**——脚本跑到 0.4 后被我停止。

## 6. 对用户三条预期的核对

| 预期 | 实测 | 判定 |
|---|---|---|
| 0.8 档持平（不低于 −3%） | 悬崖内（0.35）搬臂慢 **3.5 倍** | ❌ 证伪，"安全区里搬是纯亏" |
| 1.2 档搬臂 ≥ +15% | +40% | ✅ 成立 |
| 1.6 档双崩（目的地也满） | 1.6 档搬臂仍 0.98 命中 | ❌ 装置没造出"坏目的地"（见第 5 节：容量没被压过） |

## 7. 诚实边界

- 常驻集固定为 8 × 3000 词（≈43k = 0.38× 容量），悬崖位置只在 0.40~0.50 这一段被夹住；常驻集更小/更大时阈值会移动，未测。
- 每次"回来"只发一轮、只生成 1 个 token；真实 agent 回来会连续跑多轮，**摊销搬家成本**的情形未测（这会让搬迁更容易划算）。
- `h* ≈ 0.375` 里的 0.16 s / 0.72 s 是本文装置下的数；不同模型、不同 `max_model_len`、不同并发都会变，判据的**形式**可复用，常数要重测。
- 搬家成本按 8 个 program 均摊；单个 program 单独搬会更贵（固定开销）。
- 目的地衰减只测到 0.4×，0.6× 以上未测。

## 9. 补充：目的地在搬入之后继续写入（0.6 / 0.8 / 1.0×）

| 目的地额外写入 | 追加轮数 | 搬入+后续总量 / 容量 | 搬后命中率 | 返回耗时 |
|---|---|---|---|---|
| 0.6 × | 66 | 111,705 / 114,176（0.978×） | **0.000** | 0.686 s |
| 0.8 × | 88 | 134,540 / 114,176（1.18×） | **0.000** | 0.686 s |
| 1.0 × | 110 | 157,376 / 114,176（1.38×） | **0.000** | 0.687 s |

对照第 5 节（0 / 0.2 / 0.4× 全部 0.98），**分界落在 0.4 与 0.6 之间**，而且 0.6× 那一格的总量 111,705 仍**低于**名义容量 114,176——也就是说：

> 可用于前缀复用的容量比 `block_size × num_gpu_blocks` 略小（预留块 + 在飞请求的 KV 开销），实测拐点约在 **0.97~0.98× 名义容量**。

这与 E1 的形态完全一致：**又是一个断崖，不是渐变**（0.4 → 0.98，0.6 → 0.000）。

结论合并成一条：

```
目的地安全 ⇔ (搬入量 + 之后还会写进来的量) ≲ 0.97 × 目的地容量
```

所以"目的地空不空"本身没有独立意义——**它只是这个不等式左边的余量**。这也正是 E3 想量化的问题的一半。

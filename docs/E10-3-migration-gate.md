# E10-3 — 迁移作为兜底：按实测常数做门控判定

不新开跑次，用已测常数直接算“迁移兜底的门”能不能过（跨卡 + 严重不均 + 前缀 ≳4k 三个条件都满足时的最好情况）。

## 常数（全部来自本机实测）

| 项 | 数值 | 来源 |
|---|---|---|
| 4.5k 前缀冷预填（目标卡重算） | **0.63 s** | E3d / M6-B |
| 同前缀命中（TTFT） | **0.13 s** | E3d |
| 源卡 capture（1-token 预填） | **0.23 s** | M6-B |
| 跨卡 pull（p2p，1k 块级） | **0.14 s** | E2（0.61× 重算） |
| 单步墙钟（128 输出，这套卡） | **12.5 s** | E10-1 |
| 单步墙钟（512 输出） | **50.6 s** | E10-1 |

## 三种走法的单轮代价

| 走法 | 代价 | 相对“重算” |
|---|---|---|
| 不迁，目标卡重算 | 0.63 s | 基准 |
| 迁（阻塞：capture+pull 在请求路径里） | 0.23 + 0.14 + 0.13 = **0.50 s** | **省 0.13 s（20%）** |
| 迁（离径：pull 在后台，窗口内完成） | 0.13 s | **省 0.50 s（79%）** |

## 门控判定（判据：p50 或 TTFT 改善 ≥10%）

- 离径最好情况：0.50 s ÷ 12.5 s = **4.0%**（128 输出），0.50 ÷ 50.6 = **1.0%**（512 输出）。
- 阻塞情况：0.13 ÷ 12.5 = **1.0%**。
- **都 <10%** ⇒ 在本栈的步长下，迁移作为兜底也过不了门。

反解“什么时候能过 10%”：需要 `0.50 / step ≥ 0.10` ⇒ **单步 ≤5.0 s**。
即只有当 decode 变快（这套卡现在 9~11 tok/s，128 token 就要 12.5 s）或输出很短（≤40 token）时，迁移才可能在延迟上体现。

## 与 M6 那组 43 点提升的关系

M6 压力窗口（7.38% → 49.98/54.39%）测的是**命中率**在“单卡被压穿”时的救援效果，不是单轮延迟；那组数据成立，但它回答的是“别让卡被压穿”，而正确做法是**放置/准入**（第一段就把 24 个 program 摊开），不是事后迁移。

## 结论

1. 迁移兜底在本栈**过不了 10% 的延迟门**（最好 4.0%），除非 decode 提速 2.5 倍以上。
2. 它的价值只在“token 记账/吞吐”层面：把一次 0.63 s 的重算换成 0.14 s 的搬运，省 0.49 s 的引擎占用——这与 E10-1 的结论一致（prefill 是吞吐问题，不是延迟问题）。
3. 因此三步的最终判定：① 性能线停（prefill <10%）；② 保活按预注册判据应关（比值 1.2 < 2，且零时延收益）；③ 迁移仅在有“快 decode + 长前缀 + 严重不均”三条件同时成立时才可能有用，本栈不满足。

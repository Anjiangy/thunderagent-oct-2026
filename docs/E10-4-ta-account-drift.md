# E10-4 — TA 的账实偏差：两层，一层无害一层致命

装置：单卡 892×128 = 114,176；TA(:9001, tr) → 一张卡；6 个 program × 3000 词（实际 prompt 4,560 token，第 5 轮 7,010）× 5 轮，每轮结束后同时读 TA `/programs` 与引擎 `/metrics`。

## 实测（每 program 均值）

| 轮 | 实际 prompt | TA `context_len` | 比值 | TA `total_tokens` | 比值 |
|---|---|---|---|---|---|
| 1 | 4,560 | ≈ 23.6k（6 个 program 合计 73k 时只有 1 个入表） | — | ≈ 4.7k | ≈1.03 |
| 2 | 5,100 | 23.6k | 4.6× | 5.1k | 1.00 |
| 3 | 5,700 | 23.7k | 4.2× | 5.6k | 0.99 |
| 4 | 6,300 | 23.8k | 3.8× | 6.3k | 1.00 |
| 5 | 7,010 | 23.7k | **3.4×** | 7.2k | **1.02** |

## 两层偏差

1. **`context_len` 是字符估算，系统性高估 3.4~4.6×**（我们的文本词短、字密：3000 词 ≈ 23.7k 字符，而真 token 只有 4.6k~7k）。它用于展示与亲和判断，**不参与容量判定**，所以单独出现时无害。
2. **容量账用的是 `total_tokens`（实测 token），误差 ~2%**——这一层是准的。这就是 E5 头对头只有 1.004× 的根本原因：**TA 的容量账本来就是对的**。

## 但有一个真正会“压穿”的缺口

TA 计算“已有缓存”的公式是：

```
shared_tokens = max(0, Σ reasoning_program_tokens − kv_cache_usage_perc × 总容量)
可用判定 = (Σ active_tokens − shared_tokens + buffer) ≤ 总容量
```

本次实测引擎 `/metrics` 的 `kv_cache_usage_perc` **恒为 0.0**（该引擎实例请求结束即释放块），于是：

- `shared_tokens = 41,509 − 0 = 41,509`；
- 判定变成 `(41,509 − 41,509 + buffer) ≤ 114,176` **恒成立** → TA 认为“全部上下文都在缓存里、不占额外容量”，于是**永不节流**。

这才是“账实偏差”的致命形态：**不是 TA 估错 token，而是它把“引擎没报占用”解释成“全在缓存里”**。在生产里只要 `kv_cache_usage_perc` 缺失、恒 0（未开 prefix caching、或指标名对不上、或采到的是空闲时刻），TA 就会持续超额接纳，直到卡被打穿——这时我们的 `⌈(D−K)/p⌉` 放置才有救。

## 结论

- **偏差 1（context_len 3.4×）不会导致压穿**，只影响可观测性。
- **偏差 2（shared_tokens 把缺失的 kv_cache_usage 当成“全命中”）会导致压穿**，且它依赖部署配置而非负载。
- 所以我们之前“TA 一均衡就没我们事”的判断要修正为：**TA 只在 `kv_cache_usage_perc` 被正确上报时才稳；一旦这个指标失真，压穿会真实发生，我们的放置/兜底就有位置**。

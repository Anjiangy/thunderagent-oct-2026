## 结论（E4 可收口）

1. **budget 不是杠杆**。在引擎干净、demand=1.09 的条件下，三档 budget 的差异完全落在噪声内（≤0.16 s），因为**一次搬家都没发生**。
2. **为什么没触发**：`_balance_once` 每 5 s 扫一次，`demand = Σ已记录 prompt_tokens / capacity`；程序要各自跑过一轮才会被记账，而 3 轮会话总时长只有 ~20 s，扫到第 2~3 次时整批程序刚好跑完，窗口已经结束。
3. **此前唯一"搬了 7 次"的跑次是坏数据**：那次 A 卡 `kv_cache_usage=0.9989`（上一轮残留），真实占用被顶满才触发；换句话说，触发来自"引擎已经假死"，不是来自负载设计。
4. 因此 E4 的最终结论应写成：**在 3~6 轮的程序级会话形状下，"搬家数量"这一支不构成独立收益来源**；有效的杠杆是放置（E5 已证 1.004× 不回归）与"KV 位置入路由"。

## 顺带确认的一个真 bug（影响所有历史跑次）

A 卡跑完一轮重负载后会停在 `num_requests_running=0 && kv_cache_usage=0.9989`，此时**任何新请求挂死**（直接打 1-token 请求，重启前 30~40 s 超时，重启后 1 s 返回）。`/reset_prefix_cache` 在本构建返回 404（未开 dev mode），因此唯一解法是重启引擎。此前多轮 TimeoutError 全部由此而来。
